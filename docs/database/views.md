# Database views - generated

Regenerated from the live catalog by `scripts/docs/gen_schema_docs.sh` (the `make
docs-schema` target) on 2026-11-07. **Do not edit**: the next run replaces this file. Prose
about views belongs in `db/README.md`; the checks over them live in
`scripts/db/verify.sh`.

The extension views pg_stat_statements installs are in here as well, because the catalog does not
distinguish them; the vw_ ones belong to the project. scripts/docs/check_agent_docs.sh is the check that
the names the prose promises match this list, in both directions: advertised-and-absent, and
disclaimed-and-present.

vw_idempotency_status|invoker|One row per function that changes persistent state: which tables it writes, whether it takes an idempotency claim, whether it has a natural upsert arbiter, whether it writes a table whose version column is now maintained, and a verdict. Limitations stated because they are how this view would mislead: participation is read from function bodies, so a tool that deduplicates in Python rather than in SQL does not show up, and a function whose writes happen only through another function reports the pattern of the call it makes, not the call it should have made.

vw_timestamp_status|invoker|One row per table: whether it has a creation timestamp, whether it has an updated_at, whether that column is NOT NULL, which functions rewrite the table, which trigger maintains the column, and whether that trigger fires on UPDATE and on INSERT - with needs_attention set for the two ways the answer can be no. vw_tool_calls|invoker|One row per tool invocation, derived from agent_interactions by position: step n of actions_taken paired with step n of tool_observations. Built by 0017 as the answer to the question "what did the agent call, in what order, with what in and what out" - which is the table 4.5 found referenced and never created. It is a view and not a table on purpose: a second log of the same calls is a second implementation of ADR-001's rule, and the two copies drift, which is what §3.3 is a post-mortem for. Runs whose arrays are not both JSON arrays contribute no rows at all, so this view counts calls, never runs; vw_tool_performance carries that limit forward and says so. What it cannot tell you is which call failed: the base table records one error_message per run, and the observation's "type" is a Python class name that reads str for both a result and an error, so run_errored is a run-level fact wearing a per-call row. Making per-call failure an answer means a key on the step objects, not a parallel table.
vw_tool_performance|invoker|Per tool, per tenant: how many calls, in how many runs, how long those runs took on average, and how many of them ended in an error. The column names say which grain each number is measured at, because the version of this report in blueprint/11_interaction_logging.sql averaged and counted at the call grain using run-level values - measured, an errored run of three calls printed error_count 3, and a 900 ms run beside a 100 ms one printed 700 ms instead of 500. mean_run_duration_ms is a run duration, not a tool latency: agent_interactions has no per-step timing beyond an ISO timestamp, so the honest unit is the run. errored_run_pct is the share of runs that used this tool and reported an error anywhere in themselves - an error in another tool's step is counted here too, which is what the data supports and, after 0017, what the column admits. Built by 0017 from vw_tool_calls.
